# 한국 형사사건 RAG 법정 대결 게임 — MVP 구현 기획서

> 문서 상태: 구현 기준안 v1.1  
> 최종 수정: 2026-09-29  
> 제품 형태: PC·모바일 브라우저에서 실행되는 반응형 웹게임  
> 대상: 기획·백엔드·AI/RAG·프론트엔드 개발자

## 1. 한 줄 정의

법을 모르는 플레이어가 상식과 논리로 변론하면, 시스템이 실제 대한민국 형사 판례와 법령을 찾아 그 논리를 법률적 주장으로 강화하고 AI 상대와 겨루게 하는 1회 변론형 법정 대결 게임이다.

이 서비스는 법률 상담이나 실제 사건의 유·무죄 예측 도구가 아니다. 승패는 실제 판결이나 정답 법리를 맞혔는지가 아니라, 게임이 제시한 제한된 사실관계 안에서 어느 쪽 주장이 더 일관되고 설득력 있게 들리는지를 AI가 비교한 게임 결과다. 판례와 법령은 변론을 풍부하게 만드는 근거 자료이며, AI 판정의 법률적 정확성을 보증하지 않는다.

## 2. 제품 목표와 원칙

### 2.1 목표

- 법률 지식보다 사실을 읽고 좋은 논리를 떠올리는 능력이 플레이의 핵심이 되게 한다.
- 플레이어의 원래 주장 방향을 보존하면서 실제 판례와 법령으로 표현을 강화한다.
- 인용 근거를 사용자가 직접 확인할 수 있게 한다.
- 작은 언어 모델에서도 안정적으로 작동하도록 각 LLM 호출의 역할을 하나로 제한한다.
- 사건 기록에 없는 사실 주장, 기록에서 가능한 추론, 조건부 가정을 서로 구분한다.

### 2.2 성공 조건

MVP는 다음 조건을 만족하면 성공으로 본다.

1. 준비된 가상 사건 3개가 처음부터 끝까지 중단 없이 플레이된다.
2. 검색 결과의 상위 10개 안에 평가자가 관련 있다고 표시한 판례가 80% 이상 포함된다.
3. 생성된 변론의 판례·법령 인용이 제공된 근거와 100% 일치한다.
4. 평가용 사용자 주장 30개 중 90% 이상에서 핵심 주장 방향이 유지된다.
5. 동일 입력 반복 실행 시 JSON 파싱 성공률이 99% 이상이다.
6. 근거가 없거나 약할 때 시스템이 인용을 꾸미지 않고 `근거 부족`으로 처리한다.

### 2.3 설계 원칙

- 검색된 근거가 모델의 사전 지식보다 우선한다.
- 한 호출에는 판례 선택, 주장 작성, 판정 중 하나의 작업만 맡긴다.
- 모델 출력은 JSON Schema로 제한하고 서버에서 다시 검증한다.
- 사용자와 AI 상대에게 같은 검색·생성 절차와 같은 근거 수 제한을 적용한다.
- 출처가 확인되지 않은 판례·법령은 화면에 표시하거나 주장에 포함하지 않는다.
- 승자를 억지로 만들지 않는다. 근거가 비슷하거나 판정 신뢰도가 낮으면 무승부를 허용한다.

## 3. MVP 범위

### 3.1 포함

- 수동 제작한 가상 형사사건 3개
- 검사 또는 변호인 진영 선택
- 플레이어의 자유 입력 주장 1회
- AI 상대의 사전 정의된 주장 방향 1회
- 양측에 동일한 판례 검색 및 현행 법령 조문 검색 파이프라인 적용
- 근거가 연결된 법률형 변론 생성
- 익명화된 양측 변론 비교 판정
- 승자 또는 무승부, 판정 이유, 결정적 쟁점 표시
- 사용한 판례·법령의 식별정보, 짧은 근거문, 원문 링크 표시

### 3.2 제외

- 반론·재반론 라운드
- 실제 개인 사건 입력 및 법률 상담
- 민사·행정·헌법 사건
- 자동 가상 사건 생성
- 판결문 전체의 세밀한 청킹과 Graph RAG
- 판례 인용 그래프
- 과거 시점 법령을 완전하게 재현하는 기능
- 다중 에이전트 오케스트레이션
- 실제 유·무죄 또는 형량 예측
- 사용자 계정, 랭킹, 결제

## 4. 핵심 사용자 경험

### 4.1 한 판의 흐름

```text
사건과 쟁점 설명
  → 플레이어 진영 선택
  → 플레이어가 일반어로 주장 1개 작성
  → 양측 근거 검색 및 변론 생성
  → 양측 변론과 인용 근거 공개
  → AI 판사의 비교 평가
  → 승자/무승부, 이유, 결정적 쟁점, 근거 링크 표시
```

### 4.2 화면 구성

1. **사건 화면**: 확정된 사실, 다투는 쟁점, 주의사항을 구분해 표시한다.
2. **진영 선택 화면**: 검사와 변호인의 목표를 한 문장으로 설명한다.
3. **주장 입력 화면**: 20~500자, 주장 예시는 제공하되 정답처럼 보이지 않게 한다.
4. **변론 결과 화면**: 플레이어 원문과 강화된 변론을 나란히 보여준다.
5. **판정 화면**: 승패보다 평가 항목별 이유와 실제 인용 근거를 우선 배치한다.

### 4.3 사용자에게 반드시 보일 안내

> 이 게임은 교육·오락 목적이며 법률 자문이나 실제 사건의 판단을 제공하지 않습니다. 가상 사건만 입력하고 실제 개인정보나 사건 자료는 입력하지 마세요.

### 4.4 UI 연출 기준

법정 배경, SD 캐릭터, 페이즈 창, 제한시간, 말풍선과 재판장 진행 문구의 상세 기준은 [법정 UI·연출 가이드](./ui/법정_UI_연출_가이드.md)를 따른다. 기준 콘셉트 이미지는 [courtroom-game-flow-concept-v1.png](./ui/courtroom-game-flow-concept-v1.png)이며 수정본은 원본을 덮어쓰지 않고 버전을 올려 저장한다.

## 5. 가상 사건 설계

한 사건은 단순 사실 목록뿐 아니라 쟁점, 양측 seed, 금지된 추론을 포함한다. 그래야 모델이 사건에 없는 사실을 보충하지 않는다.

```json
{
  "case_id": "case_001",
  "title": "술자리에서 밀쳐 발생한 중상해",
  "facts": [
    {"fact_id": "F1", "text": "A와 B가 술자리에서 말다툼했다."},
    {"fact_id": "F2", "text": "A가 B를 한 차례 밀었다."},
    {"fact_id": "F3", "text": "B는 넘어지며 테이블 모서리에 머리를 부딪혀 중상을 입었다."},
    {"fact_id": "F4", "text": "A는 B에게 상해를 입힐 의도는 없었다고 주장한다."}
  ],
  "contested_issues": [
    "상해 결과에 대한 고의 또는 예견 가능성",
    "행위와 중상해 결과 사이의 인과관계"
  ],
  "prosecution_seed": "A는 사람을 밀면 넘어져 다칠 수 있다는 결과를 예견할 수 있었다.",
  "defense_seed": "한 차례 민 행위만으로 중상해 결과까지 예견하기는 어려웠다.",
  "forbidden_assumptions": [
    "A가 흉기를 사용했다.",
    "B가 먼저 폭행했다.",
    "현장 CCTV가 존재한다."
  ],
  "content_notice": "폭행 및 상해 묘사가 포함되어 있습니다.",
  "status": "published"
}
```

### 5.1 사건 작성 규칙

- 사실과 당사자의 주장을 구분한다. `A는 의도가 없었다`는 확정 사실이 아니라 당사자 주장이다.
- 양측 seed는 같은 핵심 쟁점을 반대 방향에서 다루게 한다.
- 어느 한쪽만 압도적으로 유리한 숨은 사실을 넣지 않는다.
- 실제 사건을 그대로 복제하지 않고 인명·장소·날짜를 가상화한다.
- 각 사건은 법률 실무자 또는 법률 전공 검토자의 1회 검수를 거친다.
- 사건마다 정답 진영·정답 판결은 두지 않되, 검색 품질 시험용 `gold_relevance`는 운영 데이터와 분리해 둔다.

## 6. 기술 구성

### 6.1 권장 MVP 스택

| 영역 | 권장안 | 선택 이유 |
|---|---|---|
| 웹 UI | React 또는 Next.js | 단일 게임 플로우 구현과 배포가 단순함 |
| API | Python + FastAPI | 수집·임베딩·LLM 연동 생태계가 좋음 |
| 업무 데이터 | SQLite로 시작, 필요 시 PostgreSQL | 사건·세션·실행기록 보관 |
| Vector DB | Qdrant 로컬 모드 또는 단일 컨테이너 | 메타데이터 필터와 영속성을 함께 제공 |
| 임베딩 | 한국어 성능을 검증한 다국어 임베딩 모델 | 모델명은 오프라인 검색 평가 후 고정 |
| 생성 모델 | Qwen3.5-9B | 한국어 변론·사실 구분·구조화 출력의 로컬 기준 모델 |
| 관측성 | 구조화 로그 + 실행 ID | 검색·프롬프트·인용 오류 재현 |

기준 모델은 `Qwen3.5-9B`로 확정한다. 최초 로컬 검증은 Ollama의 `qwen3.5:9b` Q4_K_M 양자화 모델로 하고, 컨텍스트는 노트북 GPU 메모리를 고려해 8,192 토큰부터 시작한다. 모델의 네이티브 최대 컨텍스트를 그대로 할당하지 않는다. 운영 코드에서는 `LLM_MODEL` 설정과 공통 모델 어댑터를 유지해 양자화 또는 추론 서버를 바꿔도 게임 규칙이 달라지지 않게 한다.

### 6.2 논리 구성

```text
Web Client
  └─ Game API
      ├─ Case Service
      ├─ Argument Pipeline
      │   ├─ Retrieval Service
      │   ├─ Precedent Selector
      │   ├─ Statute Resolver
      │   └─ Argument Writer
      ├─ Judge Service
      └─ Run/Audit Store

Offline Ingestion
  └─ 국가법령정보 공동활용 API
      → 원문 보관
      → 정규화·검증
      → 임베딩
      → Vector DB
```

온라인 게임 요청 중에 판례 전체를 외부 API에서 검색하지 않는다. 판례 검색은 로컬 인덱스로 처리하고, 법령 원문이나 출처 링크 확인에만 캐시된 API 조회를 사용한다. 외부 API 장애가 게임 전체 장애로 번지지 않게 한다.

### 6.3 웹게임 배포 구조

브라우저에는 화면과 사용자 입력 처리만 둔다. API 인증값, 판례 검색, LLM 호출, 판정 로직은 모두 서버에서 실행한다.

```text
사용자 브라우저
  → HTTPS
웹 프론트엔드
  → HTTPS API
백엔드 서버
  ├─ 게임 상태 DB
  ├─ Vector DB
  ├─ 국가법령정보 API·캐시
  └─ LLM 추론 서버 또는 외부 추론 API
```

LLM이나 Vector DB에 브라우저가 직접 접속하게 하지 않는다. 인증값 노출, 비용 남용, 판정 조작을 막기 위해 모든 요청은 백엔드를 거친다.

### 6.4 Docker와 클라우드 사용 원칙

Docker는 필수 실행 환경이 아니라 백엔드와 데이터 서비스를 동일한 구성으로 묶는 배포 수단이다. 로컬 개발 초기에는 Docker 없이도 시작할 수 있지만, 공개 배포 전에는 백엔드 컨테이너 이미지를 만드는 것을 권장한다.

| 구성요소 | Docker 필요성 | 배포 위치 |
|---|---|---|
| React/Next.js 프론트엔드 | 선택 | 정적 웹 호스팅 또는 프론트엔드 플랫폼 |
| FastAPI 백엔드 | 권장 | 관리형 컨테이너 서비스 또는 VM |
| Qdrant | 로컬 개발 시 권장 | 관리형 Vector DB 또는 영속 디스크가 있는 VM |
| SQLite/PostgreSQL | SQLite는 불필요, PostgreSQL은 관리형 권장 | 백엔드 디스크 또는 관리형 DB |
| 8B LLM 추론 | 전용 추론 이미지 사용 시 권장 | 외부 추론 API 또는 GPU 서버 |

MVP 배포는 다음 두 방식 중 하나를 선택한다.

**A. 관리형 서비스 조합 — 첫 공개 테스트 권장**

```text
정적 프론트엔드 호스팅
+ 관리형 컨테이너 백엔드
+ 관리형 DB/Vector DB
+ 외부 LLM 추론 API
```

- 서버 운영 부담이 작고 사용자가 없을 때 비용을 줄이기 쉽다.
- 서비스가 여러 곳으로 나뉘므로 환경변수와 네트워크 설정이 필요하다.
- LLM 호출 비용과 제공자 정책을 별도로 관리해야 한다.

**B. 단일 클라우드 VM + Docker Compose — 자체 운영형**

```text
Cloud VM
  ├─ reverse proxy
  ├─ web/API container
  ├─ Qdrant container
  └─ DB 또는 외부 관리형 DB
```

- 한 서버에서 이해하고 재현하기 쉽다.
- 보안 업데이트, HTTPS, 백업, 장애 복구를 직접 책임져야 한다.
- 8B 모델까지 직접 실행하면 일반 CPU VM으로는 응답이 느리므로 별도 GPU 서버가 필요할 수 있다.

첫 MVP에서는 **프론트엔드 호스팅 + Docker로 배포한 백엔드 + 외부 LLM 추론 API** 구성을 기본안으로 한다. 사용량과 비용이 확인된 뒤 LLM을 GPU 서버에 직접 올릴지 결정한다.

오픈 웨이트 모델 자체에는 건당 크레딧이 없지만 공개 서비스에서 자체 실행하려면 GPU가 장착된 클라우드 인스턴스의 실행 시간, 디스크, 트래픽 비용이 발생한다. 즉 자체 호스팅 비용은 모델 사용료가 아니라 AWS 등 인프라 사용료다. 로컬 개발 중에는 4060 노트북에서 실행하므로 별도 클라우드 비용이 없다.

로컬 개발용 `compose.yaml`에는 우선 백엔드와 Qdrant만 포함한다. 프론트엔드는 빠른 개발을 위해 로컬 개발 서버로 실행하고, LLM은 설정에 따라 로컬 추론 서버 또는 외부 추론 API로 교체할 수 있게 한다.

## 7. 국가법령정보 데이터 연계

### 7.1 선행 조건

- 개인 개발 테스트를 포함한 정식 API 호출에는 국가법령정보 공동활용 회원가입, OPEN API 신청, 개인 인증값 `OC` 발급이 필요하다. 현재 신청 화면은 OPEN API 신청이 자동승인되어 신청 직후 이용할 수 있다고 안내한다.
- API 인증값 `OC`는 서버 비밀값으로 보관하며 클라이언트에 노출하지 않는다.
- 서비스 화면과 데이터 상세 화면에 법제처 국가법령정보센터 출처를 표시한다.
- 샘플 URL의 `OC=test`는 문서 예제 확인용으로만 취급하고 수집기나 서비스의 인증값으로 사용하지 않는다.
- 이용조건과 호출 제한은 배포 전에 다시 확인한다. 별도 심사가 붙는 데이터나 신청 유형은 해당 안내를 따른다.

공식 안내상 판례는 목록 조회와 본문 조회 API로 구분된다. 목록은 `lawSearch.do?target=prec`, 본문은 판례 일련번호를 사용한 `lawService.do?target=prec` 방식이다. 본문 응답에는 사건명, 사건번호, 선고일자, 법원명, 사건종류, 판시사항, 판결요지, 참조조문, 참조판례, 판례내용이 포함된다.

### 7.2 수집 절차

1. 판례 목록을 페이지 단위로 수집한다.
2. `판례일련번호`를 기준으로 본문을 조회한다.
3. 원본 응답을 수정하지 않고 압축 보관한다.
4. 정규화 레코드를 생성하고 필수 필드를 검증한다.
5. `사건종류명=형사`인 레코드만 MVP 인덱스에 넣는다.
6. 동일 사건번호·선고일자·법원 기준 중복을 제거한다.
7. 변경·삭제 반영을 위해 수집 시각과 원문 해시를 기록한다.
8. 임베딩 모델 또는 전처리 버전이 바뀌면 새 인덱스를 만들고 원자적으로 교체한다.

### 7.2.1 API 호출 보호 정책

국가법령정보센터가 구체적인 호출 한도를 별도로 확정해 주기 전까지 다음의 보수적인 기본값을 적용한다.

```text
동시 요청 수: 1
초기 최대 호출률: 초당 1회
요청 timeout: 15초
재시도 횟수: 최대 3회
백오프: 2초 → 4초 → 8초 + 작은 무작위 지연
```

- `429`, `503`, timeout이 발생하면 즉시 속도를 낮추고 `Retry-After`가 있으면 그 값을 우선한다.
- 같은 목록 페이지와 같은 판례·법령 ID는 로컬에 캐시하여 다시 호출하지 않는다.
- 수집 진행상황을 페이지와 판례 ID 단위로 저장해 중단 후 처음부터 재호출하지 않는다.
- 실패한 항목만 별도 큐에 넣고 전체 수집 직후 몰아서 재시도하지 않는다.
- 개발·테스트에서는 작은 페이지 범위와 fixture를 사용하며 테스트 실행 때마다 실 API를 호출하지 않는다.
- 게임 플레이 중 판례 API를 실시간 반복 호출하지 않고 미리 구축한 로컬 인덱스를 사용한다.
- 전체 판례의 대량 수집, 호출률 상향 또는 다중 워커 사용이 필요해지면 작업을 중단하고 사용자에게 예상 호출량, 필요성, 위험을 먼저 알린다. 외부 기관에 전화·메일·문의하거나 협의를 요청하는 행위는 사용자의 명시적 지시 없이 수행하지 않는다.
- 호출 제한값은 환경변수로 관리하되 운영자가 명시적으로 변경하지 않는 한 기본값을 높이지 않는다.

### 7.3 판례 정규화 스키마

```json
{
  "precedent_id": "lawgo-228541",
  "source_serial_id": "228541",
  "case_name": "...",
  "case_number": "...",
  "decision_date": "YYYY-MM-DD",
  "court_name": "...",
  "court_type_code": "400201",
  "case_type_name": "형사",
  "decision_type": "...",
  "holding": "판시사항 원문",
  "summary": "판결요지 원문",
  "referenced_statutes_raw": "참조조문 원문",
  "referenced_cases_raw": "참조판례 원문",
  "full_text": "판례내용 원문",
  "source_url": "검증된 상세 링크",
  "fetched_at": "ISO-8601",
  "source_hash": "sha256:...",
  "parser_version": "1.0.0"
}
```

공식 응답에 없는 임의의 `case_id`, 자동 요약, 법률 쟁점 태그는 원문 필드와 분리하고 `derived_*` 접두어 또는 별도 테이블로 관리한다.

### 7.4 법령 데이터와 시점 문제

판례의 `참조조문`만 따라가면 사용자가 제시한 법률 논리가 관련 판례에 포함되지 않은 경우를 놓칠 수 있다. 따라서 법령은 판례의 부속 정보가 아니라 독립 검색원으로 취급한다.

MVP 법령 인덱스는 다음 순서로 구축한다.

1. 「형법」 전체를 조문 단위로 수집한다.
2. 가상 사건이 직접 다루는 특별형법이 있으면 해당 법령 전체 또는 관련 장을 추가한다.
3. 지원 사건이 확대될 때 관련 특별법을 추가한다.
4. 증거능력·절차 위반을 게임 쟁점으로 지원하기 전에는 「형사소송법」을 변론 근거 인덱스에 넣지 않는다.

공식 현행법령 API는 법령 ID와 6자리 조 번호 `JO`를 사용해 조문·항·호 단위 내용을 조회할 수 있다. 수집한 조문은 다음처럼 정규화한다.

```json
{
  "statute_article_id": "lawgo-001692:002100",
  "law_id": "001692",
  "law_name": "형법",
  "article_number": "제21조",
  "article_title": "정당방위",
  "article_text": "...",
  "effective_date": "YYYY-MM-DD",
  "source_url": "...",
  "fetched_at": "ISO-8601",
  "source_hash": "sha256:..."
}
```

판례의 `참조조문`도 계속 활용하되 보조 경로로 사용한다.

```text
판례 참조조문 원문
  → 법령명·조·항·호 파싱
  → 법령 인덱스의 식별자와 연결
  → 공식 API 원문과 재검증
```

MVP는 현행 조문만 제공하되 반드시 `현행 조문`이라고 표시한다. 판결 선고 당시 조문과 달라졌을 가능성이 있으면 판례의 참조조문 원문과 현행 조문을 구분해 보여주며, 둘이 동일하다고 단정하지 않는다. 파싱이나 조회가 불확실하면 해당 조문은 생성 모델에 넘기지 않고 `조문 확인 실패`로 기록한다.

## 8. 인덱싱 설계

### 8.1 판례 검색 문서

판례 하나를 검색 단위 하나로 시작한다. 단, 필드 경계를 보존한다.

```text
[사건명]
{case_name}

[판시사항]
{holding}

[판결요지]
{summary}

[참조조문]
{referenced_statutes_raw}
```

판시사항과 판결요지가 모두 비어 있으면 인덱싱하지 않는다. 입력이 임베딩 모델 최대 길이를 넘으면 무음 절단하지 않고 필드 우선순위에 따라 축약하거나 `holding`, `summary` 두 문서로 분리한다. 분리 여부는 검색 평가 결과로 결정한다.

### 8.2 판례 벡터 메타데이터

```json
{
  "precedent_id": "lawgo-228541",
  "case_number": "...",
  "court_name": "...",
  "court_type_code": "400201",
  "decision_date": "YYYY-MM-DD",
  "case_type_name": "형사",
  "source_url": "...",
  "document_version": "sha256:...",
  "embedding_model": "...",
  "embedding_version": "..."
}
```

### 8.3 법령 검색 문서와 메타데이터

현행 법령은 조문 하나를 검색 단위 하나로 만든다.

```text
[법령명]
{law_name}

[조문]
{article_number} {article_title}

[내용]
{article_text}
```

```json
{
  "statute_article_id": "lawgo-001692:002100",
  "law_id": "001692",
  "law_name": "형법",
  "article_number": "제21조",
  "effective_date": "YYYY-MM-DD",
  "source_url": "...",
  "document_version": "sha256:...",
  "embedding_model": "...",
  "embedding_version": "..."
}
```

판례와 법령은 같은 Vector DB를 사용하더라도 `precedents`와 `statutes_current` 컬렉션으로 분리한다. 두 검색 점수는 직접 비교하거나 하나의 순위로 합치지 않는다.

### 8.4 판례 수집 범위

사용자의 주장 방향을 사전에 모두 예측할 수 없으므로 사건 seed에 맞춘 소수 판례만으로 운영하지 않는다.

- 최종 목표는 API가 제공하는 형사 판례 전반을 점진적으로 수집하는 것이다.
- 민사·행정 등 다른 사건종류는 MVP 인덱스에서 제외한다.
- API 호출 보호 정책에 따라 한 번에 전체를 당겨오지 않고 체크포인트를 저장하며 순차 수집한다.
- UI 개발과 초기 통합은 소규모 고정 스냅샷으로 진행하지만, 이를 최종 검색 범위로 간주하지 않는다.
- 게임 공개 전에는 예상 밖 주장으로 만든 평가셋을 사용해 검색 사각지대를 점검한다.

### 8.5 갱신 전략

- 개발 중에는 고정된 데이터 스냅샷을 사용해 결과를 재현한다.
- 운영에서는 주기적으로 변경분을 수집하되 검증 완료 전 현재 인덱스를 덮어쓰지 않는다.
- 판례 삭제 또는 정정 데이터를 반영할 수 있도록 soft delete와 인덱스 버전을 둔다.

## 9. 검색 파이프라인

### 9.1 자유 주장 정규화

사용자의 주장을 사건 seed 중 하나로 분류하거나 미리 정한 주장에 끼워 맞추지 않는다. 작은 LLM 호출 하나를 사용해 검색용 쟁점만 추출한다.

입력:

```text
사건의 확정 사실 + 사용자 원문 주장
```

출력:

```json
{
  "claim_summary": "상대방의 선제공격을 막기 위한 행위였다는 주장",
  "legal_issues": ["정당방위", "방위행위의 상당성"],
  "keywords": ["현재의 부당한 침해", "방어행위"],
  "statute_hints": ["형법 제21조"]
}
```

이 단계는 사용자의 주장을 바꾸거나 새 주장을 만드는 단계가 아니다. 원문과 다른 방향으로 정규화되면 원문만으로 검색을 계속한다.

### 9.2 병렬 근거 검색

```text
원문 query = 사건 제목 + 확정 사실 + 진영 + 원래 주장/seed
쟁점 query = 확정 사실 + claim_summary + legal_issues + keywords
```

1. 입력을 1,500자 이내로 정규화한다.
2. 원문 query와 쟁점 query로 `precedents` 컬렉션을 각각 검색한다.
3. 두 결과를 합쳐 중복을 제거하고 형사 판례 후보 Top-10을 만든다.
4. 같은 두 query로 `statutes_current` 컬렉션을 검색해 현행 조문 후보 Top-10을 만든다.
5. `형법 제21조` 같은 명시적 법조문이 있으면 벡터 검색과 별도로 정확 일치 조회를 수행한다.
6. 판례 선택기는 판례를 최대 2개, 법령 선택기는 현행 조문을 최대 3개 선택한다.
7. 두 선택기는 각각 0개를 반환할 수 있으며 한쪽이 0개여도 다른 쪽의 근거는 사용한다.
8. 선택된 모든 ID와 원문은 서버에서 검증한다.

생성에 사용하는 판례는 최대 2개, 법령은 최대 3개로 제한해 컨텍스트와 인용 복잡도를 통제한다.

### 9.3 근거 선택 규칙

선택 모델은 새 법리나 요약을 만들지 않고 ID와 선택 이유만 반환한다. 판례와 법령은 별도 호출 또는 별도 출력 필드로 선택한다.

```json
{
  "selected": [
    {
      "precedent_id": "lawgo-228541",
      "supported_issue": "결과 예견 가능성",
      "support": "supports"
    }
  ],
  "insufficient_precedent": false
}
```

법령 선택 결과:

```json
{
  "selected": [
    {
      "statute_article_id": "lawgo-001692:002100",
      "supported_issue": "정당방위의 성립요건"
    }
  ],
  "insufficient_statute": false
}
```

서버 검증 규칙:

- 후보 목록에 없는 ID는 거부한다.
- 판례 2개 또는 법령 3개를 초과하면 거부한다.
- `support`는 `supports`, `distinguishes` 중 하나만 허용한다.
- 0개 선택도 정상 결과다.
- 선택된 판례 근거문이 실제 판시사항 또는 판결요지에서 확인되지 않으면 제외한다.
- 선택된 법령 명제가 조문 원문에서 확인되지 않으면 제외한다.
- 판례가 없고 법령만 있는 주장도 정상적인 생성 경로로 처리한다.
- 법령이 없고 판례만 있는 경우에도 판례의 적용 범위와 한계를 밝히고 생성할 수 있다.

### 9.4 검색 품질이 기준에 못 미칠 때의 개선 순서

1. 임베딩 모델 비교
2. 입력 필드와 전처리 조정
3. 후보 수 조정
4. 키워드 검색을 결합한 hybrid search
5. cross-encoder reranker
6. 쟁점 추출 프롬프트와 일상어-법률용어 매핑 개선
7. 판례 전문 청킹

처음부터 모든 기법을 넣지 않는다. 고정된 평가셋에서 앞 단계가 실패할 때만 다음 단계를 추가한다.

## 10. 양측 변론 생성

### 10.1 공통 입력

- 사건 ID와 확정 사실
- 진영: `prosecution` 또는 `defense`
- 플레이어 원문 또는 사건 seed
- 선택된 판례 최대 2개
- 검증된 현행 법령 조문
- 금지된 추론 목록

### 10.2 필수 생성 규칙

1. 사건에 없는 사실을 추가하지 않는다.
2. 입력 주장의 핵심 방향을 바꾸지 않는다.
3. 제공되지 않은 판례·법령·학설을 언급하지 않는다.
4. 인용은 전달된 ID만 사용한다.
5. 판례의 결론을 현재 사건의 결론처럼 단정하지 않는다.
6. 사실이 비슷한 점과 다른 점을 함께 설명한다.
7. 근거가 약하면 그 한계를 밝힌다.
8. 상대방을 비난하거나 감정에 호소하지 않는다.
9. 법률 자문이나 실제 결과 예측처럼 표현하지 않는다.
10. 숨은 사고과정은 출력하지 않고 결론과 짧은 근거만 반환한다.

### 10.3 출력 Schema

```json
{
  "side": "defense",
  "argument": "400~800자 이내의 강화된 변론",
  "claim_preserved": true,
  "fact_ids_used": ["F2", "F3", "F4"],
  "citations": [
    {
      "type": "precedent",
      "id": "lawgo-228541",
      "proposition": "이 판례가 뒷받침하는 짧은 명제"
    },
    {
      "type": "statute",
      "id": "statute-id:article-id",
      "proposition": "해당 조문과 연결되는 짧은 명제"
    }
  ],
  "limitations": ["현행 조문과 판결 당시 조문의 일치 여부는 확인하지 않음"]
}
```

### 10.4 서버 후처리

- `fact_ids_used`가 해당 사건에 존재하는지 확인한다.
- 모든 citation ID가 모델 입력에 포함됐는지 확인한다.
- 인용 명제가 해당 원문을 명백히 왜곡하면 생성 결과를 폐기한다.
- JSON 오류는 동일 입력으로 1회만 재시도한다.
- 두 번째 실패 또는 인용 검증 실패 시 템플릿 기반 `근거 생성 실패` 응답을 반환한다.
- 사용자의 원문은 강화된 변론과 별도로 그대로 보존해 의미 변형을 사용자가 확인하게 한다.

## 11. AI 상대

플레이어가 검사면 AI는 `defense_seed`, 플레이어가 변호인이면 AI는 `prosecution_seed`를 사용한다. AI는 독자 전략을 발명하지 않고 seed의 방향만 법률형 변론으로 확장한다.

양측 공정성 규칙:

- 같은 검색 후보 수와 최종 인용 수 제한
- 같은 임베딩 모델과 검색 인덱스
- 같은 변론 글자 수 범위
- 같은 생성 temperature와 토큰 상한
- 같은 검증 및 실패 처리
- 플레이어 주장을 보고 AI seed를 수정하지 않음

## 12. AI 판사

### 12.1 입력

- 사건의 확정 사실과 쟁점
- `A측`, `B측`으로 익명화한 양측 변론
- 양측이 실제로 사용한 검증된 근거문
- 동일한 글자 수 상한으로 정규화된 텍스트
- 사전 사실 점검 결과: 확인된 사실, 당사자 주장, 추론, 가정, 기록 외 사실

진영 명칭은 판정 이후에만 다시 연결한다. 입력 순서는 실행 ID를 바탕으로 무작위화해 항상 먼저 제시되는 쪽이 유리해지는 현상을 줄인다.

### 12.2 사실 점검

판정 전에 양측 주장의 문장을 다음 다섯 종류로 분류한다.

| 분류 | 의미 | 판정 처리 |
|---|---|---|
| `record_supported` | 사건 기록에 직접 적힌 사실 | 그대로 사용 |
| `party_claim` | 사건 기록에 당사자의 주장으로만 적힌 내용 | 확정 사실과 구분 |
| `reasonable_inference` | 기록을 바탕으로 한 해석 또는 추론 | 허용하되 추론으로 표시 |
| `hypothesis` | `만약`, `가령` 등 조건부 가정 | 실제 사실로 사용하지 않음 |
| `unsupported_assertion` | 기록에 없는 내용을 실제 사실처럼 단정 | 판정 근거에서 제외하고 사용자에게 표시 |

`기록에 없음`을 곧바로 거짓이라고 단정하지 않는다. 판례 속 사실도 현재 게임 사건의 사실로 옮겨 쓰지 않는다. 원문 주장은 삭제하거나 몰래 수정하지 않고 분류 결과를 별도로 붙인다.

### 12.3 평가 항목

법률적으로 옳은 결론인지를 채점하지 않는다. 다음 항목을 0~4점으로 평가한다.

| 항목 | 판단 내용 |
|---|---|
| 기록 충실도 | 사건 기록과 확인 상태를 왜곡하지 않았는가 |
| 논리 일관성 | 전제에서 결론으로 이어지는 흐름이 자연스러운가 |
| 설득력 | 상대 주장과 비교했을 때 이유와 근거가 더 납득되는가 |

### 12.4 판정 규칙

- 총점이 높은 쪽을 승자로 하되, 차이가 2점 이하이면 무승부로 처리한다.
- 사건에 없는 핵심 사실을 단정하면 기록 충실도에서 감점하고 해당 전제를 판정 근거에서 제외한다.
- 조건부 가정이나 합리적 추론은 사건 외 사실과 동일하게 제재하지 않는다.
- 판사는 새 판례·법령·사실을 추가하지 않는다.
- `유죄`, `무죄`, `형량`을 선고하지 않는다.

```json
{
  "winner": "A",
  "scores": {
    "A": {
      "record_fidelity": 4,
      "coherence": 4,
      "persuasiveness": 4
    },
    "B": {
      "record_fidelity": 2,
      "coherence": 3,
      "persuasiveness": 3
    }
  },
  "reason": "A측은 확정 사실과 결과 예견 가능성 쟁점을 더 직접적으로 연결했다.",
  "decisive_point": "행위 당시 중상해 결과의 예견 가능성",
  "unsupported_assertions": {
    "A": [],
    "B": ["현장 CCTV가 존재한다는 전제"]
  }
}
```

서버가 점수를 다시 합산해 `winner`가 규칙과 일치하는지 검증한다. UI에는 `이번 변론 승자: 검사/변호인` 또는 `이번 변론: 무승부`라고 표시한다.

## 13. API 설계

### 13.1 게임 API

| Method | Path | 역할 |
|---|---|---|
| `GET` | `/api/v1/cases` | 공개 사건 목록 |
| `GET` | `/api/v1/cases/{case_id}` | 사건 상세 |
| `POST` | `/api/v1/games` | 게임 생성, 진영 선택 |
| `POST` | `/api/v1/games/{game_id}/argument` | 플레이어 주장 제출 |
| `GET` | `/api/v1/games/{game_id}` | 진행 상태 및 결과 조회 |
| `GET` | `/api/v1/sources/precedents/{id}` | 검증된 판례 상세·출처 |
| `GET` | `/api/v1/sources/statutes/{id}` | 검증된 현행 조문 상세·출처 |

주장 제출은 중복 요청에 안전하도록 `Idempotency-Key`를 지원한다. 오래 걸리는 생성은 `queued → retrieving → generating → judging → completed | failed` 상태로 처리하고 프론트엔드는 상태를 폴링한다.

### 13.2 오류 코드

```text
CASE_NOT_FOUND
INVALID_SIDE
ARGUMENT_TOO_SHORT
ARGUMENT_TOO_LONG
RETRIEVAL_EMPTY
STATUTE_LOOKUP_FAILED
LLM_SCHEMA_INVALID
CITATION_VALIDATION_FAILED
JUDGE_FAILED
UPSTREAM_UNAVAILABLE
```

외부 API나 모델 장애를 법률적 근거 부족과 혼동하지 않도록 별도 오류로 표시한다.

## 14. 게임 상태와 저장 데이터

```text
created
  → argument_submitted
  → retrieving
  → generating
  → judging
  → completed

각 처리 상태 → failed
```

주요 테이블:

- `game_cases`: 가상 사건과 seed, 버전
- `games`: 선택 진영, 상태, 생성 시각
- `arguments`: 원문, 강화문, 진영, 버전
- `retrieval_runs`: query hash, 인덱스 버전, 후보와 점수
- `citations`: 사용된 원문 ID, 근거문, 검증 상태
- `judgments`: 익명화 순서, 점수, 결과
- `llm_runs`: 모델·프롬프트 버전, 지연시간, 파싱 성공 여부

원문 법률 데이터와 사용자 세션 데이터는 분리한다. 로그에는 API 인증값, 전체 프롬프트, 불필요한 사용자 입력 원문을 남기지 않는다.

## 15. 프롬프트와 모델 운영

- 프롬프트를 코드 문자열로 흩어두지 않고 파일 또는 DB에 버전 관리한다.
- `selector_v1`, `writer_v1`, `judge_v1`처럼 역할별로 분리한다.
- 사실 분류는 `fact_auditor_v1`, 비교 판정은 `judge_v1`으로 분리한다.
- temperature는 선택·판정 0~0.2, 변론 생성 0.2~0.4 범위에서 평가 후 고정한다.
- 생성 길이, stop token, JSON Schema, timeout, retry 정책을 호출별로 고정한다.
- 법률 원문과 사용자 입력은 명확한 구분자로 감싸고, 그 안의 지시문을 따르지 말라고 시스템 규칙에 명시한다.
- 모델 또는 프롬프트가 바뀌면 회귀 평가를 통과하기 전 운영에 반영하지 않는다.

## 16. 품질 평가

### 16.1 고정 평가셋

가상 사건 3개마다 다음을 준비한다.

- 검사 주장 5개, 변호인 주장 5개: 총 30개
- 각 주장에 관련/부분 관련/무관으로 표시한 판례 후보
- 유지되어야 할 핵심 주장 문장
- 허용 사실 ID와 금지된 추가 사실
- 예상되는 핵심 쟁점

### 16.2 오프라인 지표

| 영역 | 지표 | MVP 기준 |
|---|---|---|
| 검색 | Recall@10 | 0.80 이상 |
| 선택 | 관련 판례 precision | 0.80 이상 |
| 인용 | 존재하는 ID 비율 | 1.00 |
| 인용 | 원문이 명제를 지지하는 비율 | 0.95 이상 |
| 생성 | 주장 방향 보존 | 0.90 이상 |
| 생성 | 사건 외 핵심 사실 추가 | 0건 목표 |
| 사실 분류 | 기록 외 사실 재현율 | 0.90 이상 |
| 사실 분류 | 추론·가정의 오탐률 | 0.10 이하 |
| 구조 | JSON Schema 성공률 | 0.99 이상 |
| 판정 | A/B 순서 교환 일치율 | 0.85 이상 |

### 16.3 필수 테스트

- API 파서 fixture 테스트: 정상·누락 필드·빈 태그·인코딩 오류
- 법령 참조 파서 테스트: 조·항·호, 복수 법령, 별표, 파싱 불가 문자열
- 후보 외 판례 ID를 모델이 반환했을 때 거부하는 테스트
- 사건 외 사실 및 가짜 법령 인용 탐지 테스트
- 동일한 변론을 A/B 순서만 바꿔 판정하는 편향 테스트
- 외부 API timeout·모델 timeout·빈 검색 결과 복구 테스트
- 게임 상태 전이와 중복 제출 테스트

## 17. 보안·안전·법적 표시

- 모든 외부 입력은 길이, 문자, JSON 구조를 검증한다.
- 판례 원문과 사용자 입력을 명령이 아닌 데이터로 처리해 prompt injection을 완화한다.
- 클라이언트가 보낸 판례·점수·진영 결과를 신뢰하지 않는다.
- OPEN API 인증값과 모델 키는 서버 비밀 저장소에 둔다.
- 개발·운영 로그에서 비밀값을 마스킹한다.
- 실제 사건, 주민등록번호, 연락처 등 개인정보 입력을 금지하고 입력창에 안내한다.
- 법제처 출처를 명시하고 원문 링크를 제공한다.
- 생성 변론에는 `AI가 근거를 바탕으로 재구성한 게임용 주장`임을 표시한다.
- 위험한 폭력 묘사나 혐오 표현은 사건 제작 단계에서 최소화한다.

## 18. 관측성과 운영

각 게임에 `run_id`를 부여하고 다음을 기록한다.

- 사건·프롬프트·모델·임베딩·인덱스 버전
- 검색 후보 ID와 점수
- 최종 선택 ID와 탈락 이유 코드
- 조문 조회 성공 여부와 캐시 적중 여부
- 호출별 지연시간, 토큰 수, 재시도 횟수
- JSON 및 citation 검증 결과
- 익명화된 판정 입력 순서

원문 전체를 무조건 로깅하지 않고 재현에 필요한 식별자와 해시를 우선 기록한다. 사용자가 `근거가 맞지 않음`을 신고할 수 있게 하고 신고된 실행 ID로 재현한다.

## 19. 구현 단계와 완료 기준

### Phase 0 — 사전 준비

- API 회원가입·활용신청 및 개인 `OC` 발급
- 데이터 출처 및 이용조건 확인
- 가상 사건 3개 초안과 법률 검수자 확보
- 로컬 모델의 한국어·JSON 준수 smoke test
- Qwen3.5-9B Q4_K_M를 4060 노트북에서 8,192 컨텍스트로 실행하고 사실 분류·판정 smoke test

완료 기준: 인증값으로 판례 목록·본문과 법령 본문 샘플을 정상 조회한다.

### Phase 1 — 데이터 수집과 인덱스

- 목록/본문 수집기, 원문 저장, 정규화 파서
- 형사 판례 전반의 점진적 수집, 필터와 중복 제거
- 「형법」 및 지원 사건 관련 특별형법의 현행 조문 수집
- 판례·현행 법령 조문을 분리한 Qdrant 인덱스 생성
- 고정 평가셋 구축

완료 기준: 수집 재실행이 중복 없이 끝나고 Recall@10 0.80 이상을 달성한다.

### Phase 2 — 근거 파이프라인

- 자유 주장 쟁점 추출과 원문 보존 검증
- 사건+주장으로 판례와 현행 조문을 병렬 검색
- 판례 최대 2개 선택
- 현행 조문 최대 3개 선택
- 판례 참조조문 파싱과 법령 인덱스 연결
- citation ID 서버 검증

완료 기준: 평가셋에서 존재하지 않는 ID 인용이 0건이고 근거 부족 상태가 정상 처리된다.

### Phase 3 — 변론과 판정

- 사용자/AI 공통 변론 생성기
- 주장 방향·사실·인용 검증
- 익명화된 루브릭 판정과 무승부 처리

완료 기준: 방향 보존 90% 이상, JSON 성공률 99% 이상, 순서 교환 판정 일치율 85% 이상이다.

### Phase 4 — 게임 UI와 통합

- 사건 선택, 진영 선택, 주장 입력, 진행 상태, 결과 화면
- 원문/강화문 비교와 출처 링크
- 오류·재시도·면책 안내

완료 기준: 사건 3개×양측 진영의 6개 경로가 E2E 테스트를 통과한다.

### Phase 5 — 파일럿

- 비법률가 5명 이상 사용성 테스트
- 법률 검토자 1명 이상 근거 정확성 검토
- 지연시간·실패율·신고 사례 점검

완료 기준: 치명적 허위 인용 0건, 게임 완료율 90% 이상, 주요 사용성 문제 수정 완료다.

## 21. 주요 리스크와 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| API 신청 또는 이용조건 미확정 | 수집·배포 지연 | Phase 0에서 개인 `OC`를 발급받고 사용 범위 확인 |
| 짧은 시간의 과도한 API 호출 | 이용 제한 또는 수집 중단 | 동시 요청 1개·초당 1회 기본값, 캐시·체크포인트·백오프 적용, 대량 수집이 필요하면 중단 후 사용자에게 보고 |
| 비법률가 표현으로 검색 품질 저하 | 엉뚱한 판례 인용 | 평가셋 기반 임베딩 비교 후 hybrid/rewrite 순차 도입 |
| 현행 조문과 판결 당시 조문 불일치 | 잘못된 법 적용 인상 | 두 정보를 구분 표시하고 동일성 단정 금지 |
| 예상하지 못한 사용자 논리 | 관련 근거를 찾지 못하거나 seed 방향으로 왜곡 | 형사 판례 전반을 점진 수집하고 원문·쟁점 query로 판례와 법령을 독립 검색 |
| Qwen3.5-9B의 JSON·인용 오류 | 파이프라인 실패 | 역할 분리, Schema 검증, 후보 ID 화이트리스트, 1회 재시도 |
| AI 판사의 위치·문체 편향 | 불공정한 승패 | 진영 익명화, 순서 무작위화, 글자 수 정규화, 무승부 허용 |
| 판례가 주장을 직접 지지하지 않음 | 환각성 논증 | 0개 선택 허용, 근거 부족 공개, 인용 명제 검증 |
| 실제 법률 서비스로 오해 | 사용자 피해 | 가상 사건 한정, 반복 안내, 실제 결과 예측 금지 |

## 22. MVP 이후 확장 조건

다음 기능은 정량 지표가 필요성을 보일 때만 추가한다.

- Recall@10이 기준 미달이면 hybrid search와 reranker
- 판시사항·판결요지만으로 쟁점 구분이 안 되면 판례 전문 청킹
- 판결 당시 법령이 핵심 오류 원인이면 법령 versioning
- 플레이 시간이 짧다는 피드백이 반복되면 반론 라운드
- 사건 3개의 재방문율이 확인되면 수동 검수 사건 확대
- 판정 불일치가 높으면 이중 판정 또는 규칙 기반 보조 채점

## 23. 결정 로그

| 결정 | 이유 |
|---|---|
| 실제 유·무죄 대신 변론 승패를 표시 | 게임 평가와 법적 판단을 혼동하지 않기 위해 |
| 판례 Top-5 검색을 Top-10 후보/최대 2개 사용으로 변경 | recall을 높이되 생성 컨텍스트는 작게 유지하기 위해 |
| 승자 강제 대신 무승부 허용 | 근거 차이가 작은 경우 모델의 과신을 줄이기 위해 |
| 현재 법령을 `현행 조문`으로 명시 | 판결 당시 법령과의 불일치를 숨기지 않기 위해 |
| 법령을 판례와 별도 조문 단위 인덱스로 검색 | 판례가 없는 법률 논리와 예상 밖 사용자 주장을 지원하기 위해 |
| 좁은 사건별 판례셋 대신 형사 판례 전반을 점진 수집 | 자유 주장 게임에서 사전 정의한 논리만 검색되는 문제를 막기 위해 |
| 모델명을 설정화 | 체크포인트·양자화·배포 환경 변경에 대응하기 위해 |
| 기준 생성 모델을 Qwen3.5-9B로 확정 | 한국어·구조화 출력·로컬 실행 후보 중 우선 검증하기 위해 |
| 판정을 법률 정답이 아닌 상대적 설득력 평가로 정의 | 게임 목적상 실제 법적 결론 예측이 필요하지 않기 때문에 |
| 판례/법령 ID를 서버에서 검증 | 모델이 존재하지 않는 근거를 만드는 것을 막기 위해 |
| API 신청·인증값 발급과 출처 표시를 Phase 0으로 이동 | 구현 후 데이터 연동이나 배포가 막히는 위험을 먼저 제거하기 위해 |
